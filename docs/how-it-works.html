Anatomy of a firm agent

One job, from the moment it arrives to the moment it stops and waits for a human. Every stage runs in Google Apps Script, inside your own Workspace. Nothing here leaves your Google account unless you explicitly send it out.

Work arrives

A clock
Checks the intake sheet every few minutes. Start here.
installTrigger()
A form
A Google Form submission becomes a row.
installFormTrigger()
A webhook
Any system POSTs a row. Your site, your CRM, your case manager.
doPost(e)

All three land in the same sheet and go through the same gates. A webhook gets no shortcut.

The run, for one row

01

Claim

Status becomes Processing before any work starts, so two runs can never pick up the same matter.

RailNever touch a row that is not marked ready.
02

Precheck — the gate

Every template is read and every placeholder resolved before anything is created. One missing value and the run refuses, names the field, and writes the reason into the sheet.

RefusesNo folder. No document. Nothing to clean up.
03

Fill

Your approved Google Doc is copied and the placeholders are replaced. Same template, same row, same document, every time.

No model hereThe script writes. Nothing generates prose.
04

Review

Placeholders left behind, the client's name in every document, fee figures agreeing across documents, all documents present.

Fails toNeeds attention. No draft is made.
05

Export

Each document exported to PDF, into the same matter folder.

Optional.
06

Draft

A Gmail draft to the client, with the PDFs attached, sitting in Drafts with a human on the send button.

RailThere is no send function in the repository.
07

Call out

Optionally push to another system: Clio, Lawmatics, Slack, your own API. This is the only stage where data leaves Google.

Off by defaulthttps only, hosts you name, key in Script Properties.
08

Write back

Folder link and timestamp onto the row, so the sheet stays the place anyone can look.

—
09

Log, then stop

One line: what ran, what it produced, what needs a human. Then it waits for the next row.

RailStop and report rather than work around a problem.

Where a row ends up

Generated

Documents filed, email drafted, link on the row. A person reads it and presses send.

Needs info

It refused. The missing field is named in the notes column. Every one of these is a question your intake form is not asking.

Needs attention

It wrote something, then its own review caught a problem. Nothing went to drafts.

Can Gemini run inside this?

Yes. Apps Script can call Gemini through the same httpRequest step that calls any other API: a key from Google AI Studio kept in Script Properties, and generativelanguage.googleapis.com on the allowlist. No new code. The question worth arguing about is not whether it runs, it is where you let it stand in the pipeline.

Reasonable

  • Summarising a long document into a value a human then reads
  • Classifying a matter type or an inbound enquiry
  • Pulling a date or a name out of unstructured text, into a cell you can see
  • Drafting the body of an email that stops in Drafts anyway

Not here

  • Writing the engagement letter, or any document body
  • Supplying a value the gate refused, which is guessing with extra steps
  • Deciding a fee, a deadline, or a limitation period
  • Anything on the path between the draft and a client

A model in the pipeline is a review problem on every single matter. A template filled from a row is the same document every time. Put the intelligence in designing the agent, and keep the run deterministic. If a stage genuinely needs judgment, let the model write into a cell a human reads, never into the document a client signs.
