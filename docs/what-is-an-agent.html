What an agent actually is

Not a product you buy. A handful of text files, and somewhere for them to run. Every automation, whatever it does, is built from the same five parts — and the one that makes it safe to leave running is the one nobody talks about.

01

Every automation has five parts

Whatever you are automating, in whatever tool, it decomposes into these. Get all five written down and you have designed it. Skip one and you will find out which one at the worst moment.

Part one

Trigger

The one thing that means this work should start. Exactly one, or it never starts cleanly.

“What happens right before I would normally do this?”
Part two

Inputs

The facts the work needs, and where each one comes from. This becomes your columns.

“What do I need to know before I can start?”
Part three

Steps

What happens, in order. Each step small enough to name in a few words.

“Then what? And then what?”
Part four

Rails

What it must never do, no matter what. Written as hard rules, not preferences.

“What would be embarrassing or expensive if it happened by accident?”
Part five

Stop

Where it hands back to a person, and what it tells them. Everything ends somewhere.

“Where do I want to be the one deciding?”
02

What can start it

Five shapes, and only five. The clock is the one to start with, because it is the easiest to watch, the easiest to reason about, and the easiest to switch off.

Time

A clock

It wakes up on a schedule and asks whether there is work.

Every ten minutes. Every morning at seven. First of the month.
Submit

A form

Somebody fills something in and that submission is the start.

An intake questionnaire. A request from a colleague.
Inbound

A webhook

Another system says "this just happened" by sending a message to yours.

Your website. Your CRM. A payment. Anything with an API.
Change

An edit

Something changed in a file or a row, and the change itself is the signal.

A status flipped. A file landed in a folder.
Manual

You press run

No automation at all, and a completely reasonable place to stay.

Where everything starts, and where plenty of things should stop.
03

Before there is any script

This is the part people skip, and it is the part that decides whether the thing works. You do not start by writing code. You start by talking, and Claude does the asking.

01

Brainstorm Claude asks

You say what you do over and over. If nothing comes to mind, Claude offers a few from a list of things people in your line of work usually automate, in your words rather than in software words. You pick one. Just one.

Not your hardest job. Your most repeated one.

02

The interview Back and forth

One question at a time, waiting for each answer. What happens today, from the moment the work arrives to the moment it is done. What starts it. What it needs to know. What it produces. What it must never do. Where a person has to be involved.

It should feel like explaining the job to somebody on their first morning, because that is exactly what it is.

03

The rails conversation You decide

The one question worth slowing down for: what would be embarrassing, expensive, or a serious problem if it happened by accident? Your answers become hard rules in the code, not suggestions in a prompt. If every rail came from Claude rather than from you, this step has not really happened yet.

04

One page you can read Claude writes

Everything agreed goes into a single file, in your own words. Read it and you know everything the agent is. No jargon, no code, nothing hidden. If it says something you would not allow, you say so now and it changes.

Read this one page and you know the whole of it.

05

Now the code Claude writes

Only now. Claude turns that page into the actual script, plus the settings that point it at your own files. You do not write any of it and you do not need to read it, though it is there if you want to.

06

Into Google You paste, or Claude pushes

The script goes into Apps Script, which is a code editor Google already gives you, inside the account you already have. Either Claude pushes it there for you, or you paste the files in once. Nothing is installed, nothing is hosted, no card is needed.

07

Permission You approve

Google asks whether this script may act on your behalf. It warns you that the app is unverified, which is true: the app is the thing you just wrote. It runs as you, in your account, and nothing it touches leaves it.

04

Before you let it run unattended

Three checks, in this order. The third one is the one that actually decides whether you trust it, and most people skip it.

08

A check that writes nothing

It reads everything it would use and reports what is missing, without creating a single thing. Fix what it names, run it again, repeat until it is clean.

09

One real run, watched

One genuine piece of work, started by hand, with you looking at it. Read what it produced against what you would have produced.

10

Break it on purpose

Leave something out deliberately and watch it refuse. Then go and check that it left nothing behind: no half-finished work, nothing to tidy up. Watching it stop correctly is what earns it the right to run when you are not looking.

You are not testing whether it works. You are testing whether it stops.

11

Now put it on the clock

And learn how to switch it off before you walk away. Knowing how to stop it is what makes people willing to start it.

05

What happens on every single run

The same seven things, in the same order, every time. This is the shape of a run whether it is handling one item or a hundred.

I

Claim it Agent

Mark the work as taken, first, so nothing else picks it up and nothing gets done twice.

II

Check before doing anything

Confirm every fact it needs is actually there. Something missing means it stops now and says which thing, while stopping is still free. Nothing has been created yet, so there is nothing to undo.

III

Do the steps Agent

In the order you listed them. Nothing decided on the fly.

IV

Check its own work

Against a list you wrote. If the check fails it says so and stops, rather than passing the problem downstream.

V

Hand off, do not finish

Anything that reaches another person waits for a person to release it. Prepared, ready, not sent.

VI

Write down what it did

Back where you will look: one line, what ran, what came out, what needs you. An automation you cannot see is an automation you cannot trust.

VII

Stop

And wait for the next trigger. It does not look for more to do.

06

The rails, and why they are the point

A rail is a rule written into the code, so it holds whether or not anyone remembers it. These five carry over to almost anything worth automating.

Never guess a missing value

Something absent means stop and name it. A value filled in from what is typical is a decision nobody made.

Stopping must leave nothing behind

Check everything before creating anything. Half-finished work is worse than none, because it looks finished.

Prepare, never release

Anything going to another person gets drafted and waits. The judgment stays with whoever is accountable for it.

Never edit the output to pass a check

Fix the input or fix the template. Patching the result hides the fault, and it comes back on the next one.

Stop and report, never work around

A refusal that names the problem is a good outcome. Something built on an assumption is not.

Every refusal is information

Keep them. Each one names a question your process is not asking. That list is worth more than any of the output.

Text files, and somewhere to run them.

A page describing the job, a list of rules it cannot break, and a place that stays awake. There is no platform underneath this, nothing to subscribe to, and nothing you cannot read. The only difference between a demonstration and something real is not the files. It is the place.
